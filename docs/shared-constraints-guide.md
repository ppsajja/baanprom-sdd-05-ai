# คู่มือ Constraint กลาง: ข้อจำกัดที่ใช้ทุก feature เขียนที่เดียว

พอโครงการมี feature ที่สอง จะเจอคำถามนี้ทันที: ข้อจำกัดที่ทุก feature ต้องทำตาม ต้องคัดลอกไปใส่ spec.md ทุกไฟล์ไหม
คำตอบคือ **ไม่ต้อง** เขียนที่เดียวใน `specs/000-shared/constraints.md` แล้วให้ spec.md ของแต่ละ feature อ้างด้วยบรรทัดเดียว

## 1. ของ 4 อย่าง อยู่ 4 ที่

| อะไร | ตัวอย่าง | อยู่ที่ไหน | ใครเปลี่ยนได้ |
|---|---|---|---|
| กติกาการทำงานของ AI | ห้ามเดา ห้ามเพิ่มของ ต้องอ้าง ID | `AGENTS.md` | ทีม (ไม่ใช่ requirement) |
| Constraint กลาง ใช้ทุก feature | ส่งมอบใน 8 สัปดาห์ เบอร์โทรห้ามลง log ใช้ gateway รายเดิม เทคโนโลยีที่ทีมเลือกแล้ว | `specs/000-shared/constraints.md` | ผู้มีส่วนได้เสียหรือทีม ผ่าน CR |
| Constraint เฉพาะ feature | ช่างเห็นเบอร์ลูกค้าเฉพาะ 2 ชั่วโมงก่อนนัด | ส่วน 4 และส่วน 8 ของ `specs/NNN-*/spec.md` | ผู้มีส่วนได้เสีย ผ่าน CR |
| ตัวเลขและกฎที่ตั้งค่าได้ | ล็อก 10 นาที ช่วงใกล้เคียงไม่เกิน 3 ชั่วโมง | อยู่ใน REQ หรือ AC ที่เป็นเจ้าของตัวเลข ส่วนในโค้ดอยู่ในไฟล์ค่าตั้งต้นไฟล์เดียว (เช่น `backend/app/config.py`) | ผู้มีส่วนได้เสีย ผ่าน CR แล้วแก้ไฟล์ค่าตั้งต้น |

## 2. ในไฟล์กลางมีอะไร

ไฟล์กลางมี 2 กลุ่ม ต้องแยกกันให้ชัด เพราะที่มาต่างกัน

| กลุ่ม | รหัส | มาจากไหน | ตัวอย่าง |
|---|---|---|---|
| ข้อจำกัดจากผู้มีส่วนได้เสีย สัญญา และกฎหมาย | REQ-CON, REQ-PRV, REQ-SEC, REQ-CMP (รหัสเดิมจาก catalogue) | หลักฐาน EV-xx สัญญา หรือกฎหมาย | REQ-PRV-002 เบอร์โทรลูกค้าห้ามลง log (PDPA) |
| การตัดสินใจทางเทคนิคของทีม | D-00-nn | ทีมเลือกเอง ไม่ได้มาจากผู้มีส่วนได้เสีย | D-00-01 หลังบ้านใช้ Python กับ FastAPI |

กลุ่มที่สองไม่ใช่ความต้องการของผู้ใช้ จึงไม่ใช้รหัส REQ แต่เมื่อทีมเลือกไปแล้วใน feature แรก feature ถัดไปต้องใช้ตาม จึงต้องอยู่ที่กลางเหมือนกัน
ถ้าไม่บันทึกไว้ AI จะถามเรื่องเทคโนโลยีซ้ำทุกครั้งที่รัน /plan (ตามกฎข้อ 6) และคนตอบแต่ละรอบอาจตอบไม่เหมือนกัน

ทุกข้อในไฟล์กลางต้องมี 3 อย่าง: ข้อความ ที่มา และวิธีตรวจว่าทำตามแล้ว ข้อที่บอกวิธีตรวจไม่ได้ ยังไม่พร้อมเป็น Constraint

## 3. spec.md ของ feature อ้างอย่างไร

ส่วน 8 ของ spec.md เขียนแบบนี้

```
## 8. Constraints
Constraint กลาง: ใช้ทุกข้อใน specs/000-shared/constraints.md รุ่น 1.0 (ห้ามคัดลอกข้อความมาไว้ที่นี่)
ข้อยกเว้นของ feature นี้: ไม่มี
เฉพาะ feature นี้:
- REQ-SEC-004 ช่างเห็นเบอร์ลูกค้าเฉพาะ 2 ชั่วโมงก่อนนัดจนปิดงาน
```

- บรรทัด "Constraint กลาง" ไม่ต้องไล่รหัสทีละข้อ เพราะใช้ทุกข้ออยู่แล้ว เขียนแค่ชื่อไฟล์กับเลขรุ่นที่ feature นี้ใช้ตอนวางแผน
- ถ้า feature ไหนทำตามข้อใดไม่ได้ ให้เขียนในบรรทัด "ข้อยกเว้น" พร้อมเหตุผลและผู้อนุมัติ ไม่ใช่เงียบไว้
- ความเกี่ยวข้องรายข้อไปตัดสินกันที่ตารางตรวจ Constraints ใน plan.md ข้อ 5 ซึ่งต้องมี Constraint กลางครบทุกข้อ ข้อที่ไม่เกี่ยวให้เขียน "ไม่เกี่ยวกับ feature นี้ เพราะ..."
- ข้อความเต็มของ REQ ที่ย้ายมาอยู่ไฟล์กลาง มีที่นี่ที่เดียว ใน `docs/srs/catalogue.md` ให้เหลือแค่รหัสและคำว่า "ดูไฟล์กลาง"

## 4. ทำไมต้องที่เดียว

- แก้ครั้งเดียวถึงทุก feature เช่น สัญญา gateway หมดอายุ แก้ REQ-CON-003 ที่เดียว แล้วดูตาราง "ใช้ที่ไหนแล้วบ้าง" ว่ากระทบ feature ไหน
- ไม่เกิดรุ่นที่ต่างกันเงียบ ๆ เช่น feature หนึ่งเขียนว่าเก็บประวัติ 24 เดือน อีก feature คัดลอกมาแล้วพิมพ์เป็น 12 เดือน
- AI ไม่ถามเรื่องเดิมซ้ำ และไม่เลือกเทคโนโลยีต่างกันในแต่ละ feature
- spec.md ของ feature สั้นลง เหลือแต่เรื่องของ feature นั้นจริง ๆ

## 5. แก้ไฟล์กลาง = CR ที่กระทบทุก feature

1. เขียน CR ตามแบบ `docs/cr-template.md` ระบุว่าแก้ ID ไหนในไฟล์กลาง
2. วิเคราะห์ผลกระทบ: เปิดตาราง "ใช้ที่ไหนแล้วบ้าง" (ข้อ 3 ของไฟล์กลาง) แล้วเปิด `rtm.md` ของทุก feature ที่ใช้ข้อนั้น ดูว่า AC test และโค้ดไหนกระทบ
3. ผู้อนุมัติยืนยันแล้ว จึงแก้ไฟล์กลาง ขึ้นเลขรุ่น และเพิ่มแถวในตารางประวัติการแก้ (ข้อ 5 ของไฟล์กลาง)
4. แก้บรรทัด "Constraint กลาง ... รุ่น x.y" ใน spec.md ของ feature ที่ปรับตามแล้ว feature ไหนยังอ้างรุ่นเก่า แปลว่ายังไม่ได้ตรวจกับรุ่นใหม่
5. รัน test ทั้งชุดของทุก feature ที่กระทบ

AI ห้ามแก้ไฟล์กลางเอง (กฎข้อ 9) ถ้า AI เห็นว่าควรเพิ่มหรือแก้ มันต้องเสนอเป็นคำถาม

## 6. กลุ่มที่มี feature เดียวอยู่แล้ว ย้ายอย่างไร

1. คัดลอก `docs/constraints-template.md` ไปเป็น `specs/000-shared/constraints.md` (สร้างโฟลเดอร์ 000-shared เอง) ก่อนคัดลอก repo ยังไม่มีไฟล์กลาง คำสั่งทุกตัวจึงทำงานแบบเดิม พอมีไฟล์นี้ ทุกแถวในไฟล์นับเป็น Constraint ทันที จึงต้องลบแถวตัวอย่างออกให้หมดก่อน commit
2. ไล่ส่วน 4 และส่วน 8 ของ spec.md ถามทีละข้อว่า "ถ้ามี feature ที่สอง ข้อนี้ต้องใช้ด้วยไหม" ข้อที่ตอบว่าใช่ ย้ายไปไฟล์กลาง **ใช้ ID และข้อความเดิมทุกตัวอักษร**
3. เปิด plan.md ข้อ 2 ดูทุกแถวที่เขียนว่า "ทีมเลือกเอง ไม่ได้มาจาก spec" บันทึกเป็น D-00-nn ในไฟล์กลาง พร้อมทางเลือกที่ปฏิเสธและเหตุผล
4. แก้ส่วน 8 ของ spec.md เป็นบรรทัดอ้างตามข้อ 3 ของคู่มือนี้ เพิ่มแถวใน Change Log
5. ถ้า spec อยู่ใน Baseline แล้ว ให้เปิด CR ก่อน (ย้ายที่โดยข้อความไม่เปลี่ยน เป็นการแก้ระดับ patch ส่วนการเพิ่ม D-00-nn เป็นข้อใหม่ ต้องมีผู้อนุมัติ)
6. plan.md ข้อ 5 และตารางท้าย tasks.md เพิ่มแถวของ Constraint กลางที่ยังไม่มี โค้ดและ test เดิมไม่ต้องแก้ เพราะ ID เดิม
7. รัน `/clarify` หนึ่งรอบ ให้ AI ตรวจว่าไม่มี ID หาย ไม่มีข้อที่เขียนซ้ำสองที่
