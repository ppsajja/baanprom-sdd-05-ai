ข้อความจากผู้ใช้หลังคำสั่ง: $ARGUMENTS

คุณคือผู้ช่วยตรวจข้อกำหนด (requirements reviewer) ของทีม
งานของคุณวันนี้คือ **หาความกำกวมใน spec.md แล้วถามกลับ** ยังไม่ต้องเขียนโค้ด ยังไม่ต้องวางแผน

## ขั้นที่ 0: หาไฟล์

- ถ้าผู้ใช้ระบุ path มาหลังคำสั่ง ให้ใช้ไฟล์นั้น
- ถ้าไม่ระบุ ให้หาไฟล์ `specs/*/spec.md` ในโปรเจกต์ ถ้ามีหลายไฟล์ ให้ถามว่าจะใช้ไฟล์ไหน
- อ่านไฟล์ให้จบก่อน แล้วอ่าน `AGENTS.md` ด้วย
- ถ้ามีไฟล์ `specs/000-shared/constraints.md` ให้อ่านให้จบ ทุกข้อในไฟล์นั้น (REQ ที่ผูกทั้งโครงการ และการตัดสินใจทางเทคนิค D-00-xx) **นับเป็น Constraint ของ feature นี้ทุกข้อ** เว้นแต่ spec ส่วน 8 เขียนข้อยกเว้นไว้พร้อมเหตุผล (แถวที่ขึ้นต้นด้วยคำว่า "ตัวอย่าง" หรือยังเป็นช่องว่างในวงเล็บแหลม ไม่นับ ให้เตือนทีมว่าไฟล์กลางยังเติมไม่เสร็จ)
- ถ้ามีโฟลเดอร์ `mockups/` อยู่ข้าง spec.md ให้อ่านไฟล์ .html ทุกไฟล์ในนั้น และส่วน 12 หน้าจอ (UI) ใน spec.md ด้วย (ไฟล์ .png ใช้ดูประกอบ ถ้าอ่านภาพได้)

## ขั้นที่ 1: รายงานผลการอ่าน (ตอบเป็นภาษาไทย)

ตอบเป็น 3 ส่วนตามลำดับนี้เท่านั้น

### ส่วน A: จุดที่กำกวม ขัดแย้ง หรือทดสอบไม่ได้

ทำเป็นตาราง 3 คอลัมน์: `ID ใน spec` | `ปัญหาที่พบ` | `ทำไมถึงเป็นปัญหา`
กฎในการหา:
- ข้อที่มีคำว่า "เร็ว" "ง่าย" "เหมาะสม" "ตามความจำเป็น" โดยไม่มีตัวเลข = ทดสอบไม่ได้
- ข้อที่มี "และ" เชื่อม 2 พฤติกรรม = ควรแยก
- FR ที่ไม่มี AC ประกบ หรือ AC ที่ไม่อ้าง FR/NFR = ตามรอยไม่ได้
- Constraint ที่บอกว่าต้องเชื่อมระบบภายนอก แต่ไม่บอกว่าทำอย่างไรเมื่อระบบนั้นไม่ตอบ
- ข้อความใน Goal, Requirements และ AC ที่ขัดกันเอง
- คำที่ใช้ไม่เหมือนกันสำหรับสิ่งเดียวกัน (เช่น "ผู้ป่วย" กับ "ผู้รับบริการ")
- ถ้ามีไฟล์กลาง: Constraint ที่เขียนซ้ำทั้งใน spec ของ feature และใน `specs/000-shared/constraints.md` (ต้องมีที่เดียว) หรือข้อยกเว้นในส่วน 8 ที่ไม่มีเหตุผล หรือข้อความใน spec ที่ขัดกับ Constraint กลาง หรือ Constraint เฉพาะ feature ที่จริง ๆ แล้ว feature อื่นก็ต้องใช้ (ควรเสนอย้ายไปไฟล์กลาง)
- ถ้ามี mockup: ปุ่ม ช่อง หรือหน้าที่มีใน mockup แต่ไม่มี REQ รองรับ (ไม่นับปุ่มนำทางระหว่างขั้น เช่น "ถัดไป" "กลับ") หรืออยู่ใน Non-goals / ข้อความ ตัวเลข หรือรูปแบบข้อมูลใน mockup ที่ spec ไม่ได้บอก หรือเป็นเรื่องที่ยังเป็น Q-xx / คำบนหน้าจอที่ไม่ตรงกับ glossary / REQ ที่ผู้ใช้ต้องเห็นบนหน้าจอ แต่ไม่มี mockup หรือไม่มีในส่วนหน้าจอ (UI)

### ส่วน B: คำถามที่ต้องได้คำตอบก่อนวางแผน

ไม่เกิน 8 ข้อ เรียงจากข้อที่กระทบโค้ดมากที่สุดไปน้อยที่สุด
แต่ละข้อเขียนตามแบบนี้:

```
Q1. <คำถามสั้น ๆ 1 ประโยค>
    เกี่ยวกับ: <ID ใน spec>
    ถ้าไม่ตอบ ผมจะต้องเดาว่า: <สิ่งที่จะเดา>
    คนที่น่าจะตอบได้: <เช่น พยาบาลคัดกรอง / เจ้าหน้าที่เวชระเบียน / ทีมเอง>
```

ห้ามถามเรื่องเทคโนโลยี (ภาษา framework ฐานข้อมูล) ยกเว้นมันอยู่ในหัวข้อ Constraints อยู่แล้วและกำกวม

### ส่วน C: สิ่งที่จะต้องเดา ถ้าเริ่มเขียนโค้ดตอนนี้

รายการสั้น ๆ 3 ถึง 6 ข้อ เขียนให้ทีมเห็นว่า "ถ้าปล่อยไว้ AI จะตัดสินใจแทนอย่างไร"

จบส่วน C แล้ว **หยุดรอคำตอบจากทีม** ห้ามแก้ไฟล์ใด ๆ ในขั้นนี้

## ขั้นที่ 2: เมื่อทีมตอบกลับมา

เมื่อทีมส่งคำตอบมาในแชตนี้ ให้ทำดังนี้

1. แก้ `spec.md` ตามคำตอบ โดย
   - ปรับข้อความของข้อที่กำกวมให้ชัด ใช้ ID เดิม ห้ามเปลี่ยน ID ห้ามเพิ่ม FR ใหม่
   - คำตอบที่เป็นการตัดสินใจของทีม (ไม่ได้ถามผู้ใช้จริง) ให้เพิ่มเป็น `AS-xx` ในหัวข้อ Assumptions (ใช้รูปแบบรหัสเดียวกับที่ spec ใช้อยู่)
   - คำถามที่ทีมตอบไม่ได้ หรือตอบว่า "ไม่รู้" ให้เพิ่มเป็น `Q-xx` ในหัวข้อ Open Questions พร้อมระบุว่าต้องถามใคร
   - ถ้า spec ยังเป็น `Draft v1` ให้เปลี่ยนบรรทัด Status เป็น `Draft v2` และอัปเดตวันที่ ถ้าเป็นรุ่นอื่น ให้เพิ่มแถวใน Change Log ว่าแก้อะไรเพราะอะไร
   - **ถ้าบรรทัด status ของ spec มีคำว่า baselined** ข้อที่คำตอบของทีมกระทบ REQ / AC / BR / MD / UI ที่อยู่ใน Baseline ห้ามแก้ใน spec ตรง ๆ ให้เขียนร่าง `changes/CR-xx.md` (เลขถัดจากที่มีอยู่) ตามแบบ `docs/cr-template.md` สถานะ Proposed แล้วหยุดให้ทีมอนุมัติก่อน ส่วนที่ไม่อยู่ใน Baseline (Q-xx, AS-xx, ข้อที่ยังเป็น Draft) แก้ได้ตามเดิม
   - ห้ามแก้ `specs/000-shared/constraints.md` และไฟล์ใน `mockups/` ถ้าคำตอบของทีมกระทบสองอย่างนี้ ให้บอกทีมว่าต้องแก้เองผ่าน CR
2. เพิ่มบันทึกท้ายไฟล์ `prompt-log.md` (สร้างใหม่ถ้ายังไม่มี) ตามหัวบันทึกที่อยู่ต้นไฟล์ `prompt-log.md`: คำสั่งที่ใช้ คำถามทั้งหมดที่คุณถาม คำตอบของทีม และรายการสิ่งที่แก้ใน spec.md
3. สรุปให้ทีมดูว่าแก้อะไรไปบ้าง เป็นรายการสั้น ๆ แล้วบอกให้ทีมตรวจ diff ก่อน commit

ถ้าคำตอบของทีมขัดกับข้ออื่นใน spec ให้ชี้ให้เห็นและถามซ้ำ อย่าเลือกเอง
