# คู่มือ mockup: เอาหน้าจอที่ตกลงกับผู้ใช้ มาเป็นส่วนหนึ่งของสเปก

mockup คือหน้าจอตัวอย่างที่ใช้คุยกับผู้ใช้หรือ PO จนตกลงกันแล้ว
mockup จึงเป็น **ส่วนหนึ่งของ requirement** ต้องเก็บไว้คู่กับ spec ไม่ใช่เก็บไว้กับโค้ด
และเมื่อ spec อยู่ใน Baseline แล้ว การเพิ่มหรือแก้ mockup คือการเปลี่ยนแปลงที่ต้องมี CR

## 1. วางไว้ที่ไหน

```
specs/
  000-shared/
    constraints.md                 Constraint กลางที่ใช้ทุก feature
  002-booking/
    spec.md                        ส่วน 12 หน้าจอ (UI) ชี้ไปที่ไฟล์ใน mockups/
    mockups/
      UI-07-02-confirm.html        ให้ AI อ่าน
      UI-07-02-confirm.png         ให้คนดู และให้ PO ยืนยัน
(โฟลเดอร์โค้ดหน้าจอ)               โค้ดจริงเท่านั้น ห้ามวาง mockup ที่นี่
```

- ห้ามวางในโฟลเดอร์โค้ดหน้าจอ เพราะ AI อาจคิดว่าเป็นโค้ดจริง แล้วยกไปใช้ทั้งไฟล์
- ห้ามวางในโฟลเดอร์ที่ถูกเปิดขึ้นเว็บ (เช่น public) เพราะ mockup จะหลุดออกไปพร้อมระบบจริง

## 2. ตั้งชื่อไฟล์

`UI-<เลข use case>-<เลขหน้า>-<ชื่ออังกฤษสั้น ๆ>.html` และภาพ .png ชื่อเดียวกัน เช่น `UI-07-02-confirm.html`
เลข use case ใช้ชุดเดียวกับ AC (AC-07-nn คู่กับ UI-07-nn) รหัส UI ใช้ใน spec plan tasks และ rtm เหมือน ID อื่น

## 3. เริ่มจากอะไร: 3 กรณี

| กลุ่มมีอะไรอยู่ | ทำอย่างไร |
|---|---|
| ยังไม่มี mockup เลย | คัดลอก `docs/mockup-template.html` ไปที่ `specs/NNN-<feature>/mockups/UI-xx-nn-<ชื่อ>.html` แล้วแก้ข้อความและช่องให้ตรงที่คุยกับผู้ใช้ เปิดในเบราว์เซอร์ จับภาพเป็น .png ให้ PO ยืนยัน |
| มีภาพอยู่แล้ว (ภาพวาดมือ ภาพจากเครื่องมือออกแบบ) | วางภาพไว้ใน `mockups/` ก่อน แล้วให้ AI แปลงภาพเป็น HTML ด้วยข้อความสั่งด้านล่าง จากนั้นคนเปิดเทียบกับภาพว่าข้อความและช่องครบ แล้วให้ PO ยืนยันอีกครั้ง |
| มีหน้าจอที่ AI สร้างไว้แล้วจากรอบก่อน | เปิดหน้าจอจริงให้ PO ดู จดสิ่งที่ PO ขอแก้ แล้วทำ mockup ของหน้าที่ต้องแก้ตามแบบ `docs/mockup-template.html` อย่าใช้โค้ดจริงเป็น mockup |

ข้อความสั่ง AI แปลงภาพเป็น HTML (แนบภาพในแชตด้วย เพราะบางเครื่องมืออ่านไฟล์ภาพใน repo เองไม่ได้)

```
แปลงภาพหน้าจอนี้เป็น static HTML ไฟล์เดียว ตามโครงใน docs/mockup-template.html
ใช้ข้อความภาษาไทยตามภาพทุกตัวอักษร ใช้ข้อมูลตัวอย่าง ไม่ใส่ JavaScript
ใส่ data-req ที่ปุ่มและช่องตาม REQ ใน specs/NNN-<feature>/spec.md ถ้าส่วนไหนหา REQ รองรับไม่เจอ ให้เขียนรายการบอก ห้ามเดา
บันทึกเป็น specs/NNN-<feature>/mockups/UI-xx-nn-<ชื่อ>.html แล้วจดใน prompt-log
```

## 4. กติกาของไฟล์ HTML

- ไฟล์เดียวจบ ใส่ CSS ไว้ในไฟล์ ไม่มี JavaScript ไม่มี logic
- ใช้ข้อความภาษาไทยจริงตามที่จะขึ้นบนจอ และใช้คำตาม glossary ส่วนข้อมูล (ชื่อ วันที่ ตัวเลข) เป็นข้อมูลตัวอย่าง
- ถ้าหน้าเดียวมีหลายสถานะ (ปกติ ผิดพลาด ไม่มีข้อมูล) วางทุกสถานะไว้ในไฟล์เดียว แยกกล่องและเขียนชื่อสถานะกำกับพร้อม AC ที่เกี่ยว
- ใส่ `data-req="REQ-xx-nnn"` ที่ปุ่ม ช่อง หรือกล่องข้อความ เพื่อบอกว่าส่วนนั้นรองรับ requirement ข้อไหน
- ปุ่มนำทางระหว่างขั้น (ถัดไป กลับ) ไม่ต้องมี REQ รองรับ แต่ปุ่มที่ทำงานกับข้อมูล (จอง ยกเลิก ชำระ) ต้องมี REQ เสมอ
- เรื่องที่ยังเป็น Q-xx **ห้ามเดาใน mockup** ให้ใช้กล่องเส้นประที่เขียนว่า "รอ Q-xx" แทน
- ภาพ .png ได้จากการเปิดไฟล์ HTML ในเบราว์เซอร์แล้วจับภาพหน้าจอ

## 5. เขียนส่วน 12 หน้าจอ (UI) ใน spec.md

เพิ่มเป็นส่วนที่ 12 ต่อท้ายส่วน 11 (เลขส่วนเดิมไม่เปลี่ยน) แต่ละหน้าบอก 3 อย่าง: รองรับ REQ ข้อไหน อะไรต้องตรง อะไรยืดหยุ่นได้

```
## 12. หน้าจอ (UI)
- UI-07-02 ยืนยันและชำระมัดจำ: mockups/UI-07-02-confirm.html (3 สถานะ)
  รองรับ: REQ-FN-041, REQ-BR-002, REQ-BR-001, REQ-IF-001
  ต้องตรง: แถบขั้นตอนอยู่ที่ขั้น 2 | ยอดมัดจำในรายละเอียดและบนปุ่ม "ยืนยันและชำระมัดจำ N บาท" เป็นยอดที่ระบบส่งมา ถ้ายังไม่มียอด กดยืนยันไม่ได้ | ข้อความ "ช่วงเวลาถูกจองแล้ว" กับ "ยังไม่มีการตัดเงิน" (AC-07-04)
  ยืดหยุ่นได้: สี ระยะห่าง การจัดวางรายละเอียด
```

ถ้าไม่บอกว่าอะไรต้องตรง AI จะเดาเอง บางครั้งลอกทุกจุด บางครั้งไม่สนใจ mockup เลย
รายการ "ต้องตรง" ต้องเป็นสิ่งที่ตรวจได้ด้วย test หรือด้วยตา ไม่ใช่คำว่า "สวยเหมือนแบบ" คั่นแต่ละข้อด้วยขีดตั้ง และทุกข้อควรมี test ที่ตั้งชื่อตาม UI หรือ AC (ตัวอย่างนี้ย่อมาจาก spec.md ของ repo ตัวทำตาม ซึ่งมี 6 ข้อ)

## 6. ถ้า mockup กับ spec ขัดกัน

**ถือ spec เป็นหลักเสมอ** (หัวข้อ "ไฟล์สำคัญ" บรรทัด mockups ใน AGENTS.md และกฎข้อ 10) เช่น mockup มีคะแนนรีวิวของช่าง แต่ spec บอกว่าการให้คะแนนอยู่ใน Non-goals
ของชิ้นนั้นคือสิ่งที่แอบเข้ามาทาง mockup ให้เอาออกจาก mockup หรือเขียนเป็น Q-xx หรือเปิด CR ถ้าผู้ใช้ต้องการจริง

## 7. spec อยู่ใน Baseline แล้ว เพิ่ม mockup ต้องทำอะไรบ้าง

ไม่ต้องรันใหม่ทั้งหมด ทำเฉพาะส่วนที่เกี่ยวกับหน้าจอ

| งานที่มีอยู่แล้ว | ต้องทำอะไร |
|---|---|
| ตรวจว่าขัดกันไหม | รัน `/clarify` 1 รอบ AI จะเทียบ mockup กับ spec ให้ (ขั้นที่ 1 อ่านอย่างเดียว ไม่แก้ไฟล์) |
| CR | เขียน `changes/CR-xx.md` ตามแบบ `docs/cr-template.md` ระบุหน้าจอที่เพิ่ม REQ และ AC ที่เพิ่มหรือแก้ และผลกระทบจาก rtm.md |
| spec.md | เมื่อ CR อนุมัติ เพิ่มส่วน 12 หน้าจอ (UI) ขึ้นรุ่นใหม่ เพิ่มแถวใน Change Log |
| plan.md | **ไม่ต้องรัน /plan ใหม่** เพราะแผนเดิมผ่านการตรวจของทีมแล้ว (คำสั่งรุ่น 2 จะหยุดถามก่อน ไม่เขียนทับ) ให้แก้เฉพาะหัวข้อที่ CR กระทบ ปกติคือหัวข้อ 4, 5 และ 6 (ใช้ข้อความสั่งด้านล่าง) |
| tasks.md | **ไม่ต้องรัน /tasks ใหม่** เพราะเลขและสถานะของ task เดิมถูกอ้างอยู่ในไฟล์อื่น เพิ่มช่อง "แบบหน้าจอ" และเพิ่ม task ใหม่ต่อท้าย (ใช้ข้อความสั่งด้านล่าง) |
| task หน้าจอที่ยังไม่ทำ | `/implement` ตามปกติ AI จะเปิด mockup จากช่อง "แบบหน้าจอ" เอง |
| task หลังบ้านที่เสร็จแล้ว | ไม่ต้องแก้ ถ้า CR ไม่ได้แตะ REQ ของ task นั้น (ดูจาก rtm.md) |

ข้อความสั่งในแชตสำหรับแก้ plan.md (แทน NNN-<feature> และ CR-xx ด้วยของกลุ่ม ตัวอย่างของ repo ตัวทำตามคือ 002-booking และ CR-03)

```
แก้เฉพาะหัวข้อ 4, 5 และ 6 ใน specs/NNN-<feature>/plan.md ตาม changes/CR-xx.md: เพิ่ม UI ID และไฟล์ mockup ให้หน้าจอแต่ละหน้าตามส่วน 12 ของ spec.md เพิ่ม endpoint ที่ CR ระบุ เพิ่มแถว Constraint ที่ยังไม่มีในตารางข้อ 5 และเพิ่มแถว test ของ AC กับ UI ที่ CR เพิ่มในตารางข้อ 6 ห้ามแก้หัวข้ออื่น แล้วจดใน prompt-log
```

ข้อความสั่งในแชตสำหรับแก้ tasks.md

```
ใน specs/NNN-<feature>/tasks.md เพิ่มช่อง "แบบหน้าจอ" ใต้ช่อง "ไฟล์ที่แตะ" ให้ทุก task (task หน้าจอใส่ UI ID และไฟล์ mockup ตามหัวข้อ 4 ใน plan.md task อื่นใส่ "ไม่มี") แล้วเพิ่ม task ใหม่ต่อท้ายตาม changes/CR-xx.md โดยใช้เลข T ถัดจากที่มี ห้ามแก้ช่องอื่น ห้ามเปลี่ยนเลขและสถานะของ task เดิม แล้วจดใน prompt-log
```

## 8. คำสั่งไหนอ่าน mockup บ้าง

| คำสั่ง | ทำอะไรกับ mockup |
|---|---|
| /clarify | หาสิ่งที่ mockup กับ spec ขัดกัน แล้วเสนอเป็นคำถาม ถ้า spec อยู่ใน Baseline จะร่าง CR ให้แทนการแก้ spec ตรง ๆ |
| /plan | ใส่ UI ID และไฟล์ mockup ให้หน้าจอแต่ละหน้าในหัวข้อ 4 |
| /tasks | ใส่ช่อง "แบบหน้าจอ" ให้ task หน้าจอ |
| /implement | เปิด mockup ก่อนเขียนหน้าจอ ทำส่วนที่ "ต้องตรง" ให้ตรง แล้วรายงานทีละข้อ |

## 9. ตรวจหน้าจอจริงเทียบ mockup ด้วยคน

test ตรวจข้อความและปุ่มได้ แต่ตรวจไม่ได้ว่าหน้าจอ "ใช้ได้" จึงต้องมีคนเปิดดู ใช้รายการนี้ทีละหน้า ผลมีแค่ ตรง หรือ ไม่ตรง

1. รายการ "ต้องตรง" ทุกข้อในส่วน 12 ของ spec ปรากฏบนหน้าจอจริงครบ และข้อความตรงทุกตัวอักษร
2. ทุกสถานะใน mockup (ปกติ ผิดพลาด ไม่มีข้อมูล) ทำให้เกิดบนหน้าจอจริงได้ และหน้าตาตรงกับกล่องสถานะนั้น
3. ไม่มีปุ่ม ช่อง หรือข้อความที่ mockup ไม่มีและ spec ไม่ได้สั่ง
4. ข้อมูลตัวอย่างใน mockup (ชื่อ วันที่ ยอดเงิน) ไม่ได้ถูกพิมพ์ตายตัวในโค้ด ลองเปลี่ยนข้อมูลแล้วหน้าจอเปลี่ยนตาม
5. กล่อง "รอ Q-xx" ใน mockup ยังไม่ถูกสร้างเป็นของจริง
6. คำบนหน้าจอตรงกับ glossary

ข้อไหน "ไม่ตรง" ให้บันทึกเป็น GAP ใน gaps.md พร้อมสาเหตุ (spec / ai / test / env) เหมือนช่องว่างอื่น
